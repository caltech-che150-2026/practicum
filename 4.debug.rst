Lesson 4: Debugging, readability and data management
==================================================

In this workshop, we will learn about other "good" coding practices.

Debugging
---------

With the advent of coding agents, manual debugging is becoming less necessary. However, sometimes manual debugging is still faster, and may
allow you to understand what is going on.

Most programming languages have a built-in debugger, which allows you to run your code step by step and inspect values of variables. 
For Python, the built-in debugger is bundled with the VS Code's Python extension.

    - ``.py`` files can be debugged in VS Code by clicking the "Run and Debug" button on the left panel.
    - ``ipynb`` files can be debugged in VS Code by clicking the "Debug Cell" button on the top right of each cell, or by "Enter + Shift + Alt + Enter" on the keyboard.

Readability
-----------

"Readability" is a **subjective** measure of how easy it is to read and understand a piece of code. 
It depends on your familiarity with the programming language, and personal style. Here are some factors that improve readability:

    1. Use descriptive variable names. For example, ``x`` is not as descriptive as ``T`` for temperature.
    2. Use consistent indentation and spacing.
    3. Use smaller, modular functions instead of one large function.
    4. Use comments to explain what your code is doing.
    5. Use docstrings and meaningful function names to explain what your functions are doing. Your functions should look like
        .. code-block:: python

            def square(x: float):
                """
                This function takes a float and returns its square.

                Input:
                    x: float
                        The input float to be squared.
                Returns:
                    y: float
                        The square of the input float.
                """
                y = x**2
                return y
    6. Use packages where possible. For example, ``numpy.trapz`` is more readable than implementing the trapezoidal rule yourself.

Here are some factors that may negatively affect readability:

    1. Optimization. Sometimes the optimized code is less readable. There is usually a trade-off between development speed and execution speed.
        - The prime example is the use of vectorization in Python (which we have talked about in `performance`). For example, the following code is more readable than the vectorized version:

        .. code-block:: python

            def pairwise_distances(points):
                """
                Returns the pairwise distances between a list of points in 2D.

                Input:
                    points: (n, 2) numpy array
                        A list of n points in 2D, where each point is represented (x, y).
                Returns:
                    dist: (n, n) numpy array
                        The pairwise distance between the points, where dist[i, j] is the distance between points[i] and points[j].
                """
                n = len(points)
                dist = np.zeros((n, n))
                for i in range(n):
                    for j in range(n):
                        dist[i][j] = np.linalg.norm(points[i] - points[j])
                return dist
                
            def pairwise_distances_vectorized(points):
                """
                Returns the pairwise distances between a list of points in 2D.
                """
                diff = points[:, np.newaxis, :] - points[np.newaxis, :, :]
                return np.sqrt((diff ** 2).sum(axis=-1))
    
    2. AI Usage. We encourage the use of coding agents, but here are considerations.
        - While coding agents allow things to be done, trying to reuse code for a slightly different purpose often results in bloated code. 
        - Agents are also prone to overengineering, worrying about bugs and edge cases that will rarely occur.
        - Bloated AI codes require AI to understand and maintain, leading to more AI dependence.

Readability for coding agents
-----------------------------

It is tempting to think readability no longer matters, since an agent can read any code in seconds.
But code only tells you *what is computed*. It cannot tell you *what the numbers mean*: units, the order
of entries in an array, or whether a variable is ``V`` or ``log10(V)``. If that information is not written down,
neither you nor the agent can recover it.

We can test this with the CSTR design code from HW3 Problem 2.
Please refer to ``practicum/workshop_4/docstring_demo``, which contains two copies of the same package ``cstr``:

    - ``bare/``: the code with all docstrings and comments removed (including the ``# L/s`` comment in the original solution).
    - ``documented/``: the **identical** code with short docstrings stating units, array orderings, and conventions.

For example, in ``reactor.py``:

.. code-block:: python

    # bare/
    q = 1.0

    # documented/
    q = 1.0  # volumetric flow rate [L/s]; residence time tau = V / q [s]

We gave fresh agents (Claude Code subagents) one of the two packages, three runs each, with two different prompts in ``prompt.md``.

What we learned:

    1. Docstrings did **not** save tokens or time in a meaningful way. The run-to-run variation was larger than any difference between the two versions.
       The documented code is longer, so the agent reads *more*.
    2. The agents were good at reading code. Without any docstrings, they all worked out that ``10.0**v`` means
       logspace :math:`\log_{10} V`, that index 2 of the output is :math:`c_C`, and that :math:`T` is in K. On the actual homework problems, all numbers were correct.
    3. What the agents could not do is recover information that is not in the code, here the time unit.
       On the homework problems, most bare-code agents said the units were unknown, but one put a wrong unit on a plot without mentioning it.
       When asked for a number, every bare-code agent assumed L/min and reported 500 min. They did list this as an assumption,
       but the answer was still wrong, and it is easy to miss an assumption with heavy AI usage.
    4. Wrong documentation is worse than none. Incorrect comments greatly hinder an LLM's understanding of code. Keep commnets, docstrings
       up to date when you change the code.


The bottom line: write docstrings for the things code cannot say (units, conventions, assumptions), not for things the code already says.
Six runs per test is a small sample; your results will vary.

Data Management
---------------
Unlike homework assignments, real-world projects often involve managing many data points generated by experiments or simulations.
The settings (aka metadata) and result can be stored in a variety of formats, including text files, CSV files, Excel files, and databases.

For the simplest datasets, python package ``pandas`` is great for managing data. 
    - It can read and write data in a variety of formats, including CSV, Excel, and SQL databases.
    - You can use ``pandas`` to filter, sort, and group data.

A common pattern is to save each run to its own file, and keep an **index** (or catalog): a single table with one row per run,
listing every setting used for that run and the name of the file holding its result. To find a run, you filter the index instead of opening every file.

Do coding agents manage data for you?
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

We gave fresh agents (Claude Code subagents) the enzyme kinetics notebook from ``practicum/workshop_4/sweep.ipynb``, with the
cataloging code removed. Their task was to complete ``simulation`` and run the 10 × 10 sweep over temperature and enzyme concentration.
We never mentioned an index, catalog, or metadata.

.. list-table::
   :header-rows: 1

   * - Prompt
     - Saved results to disk
     - Wrote an index
   * - "Run the sweep" (2 runs)
     - 0/2 (results only in memory and in the notebook)
     - 0/2
   * - "... Save the results of every simulation run to disk." (6 runs)
     - 6/6
     - 3/6
   * - "... Save the results of every simulation run to its own file on disk." (6 runs)
     - 6/6
     - 4/6

What we learned:

    1. Agents do what you ask, and not much more. If you don't ask them to save results, they don't.
    2. Whether you get an index is a coin flip. The agents that skipped it put the parameters in the file names and inside each file,
       so nothing was lost, but finding "all runs at 300 K" means opening 100 files instead of filtering one table.
    3. **Indexes only recorded what was swept.** The notebook never specifies the simulation time, so each agent picked one: anywhere from 100 s
       to 20 000 s. This choice changes the results completely. At 20 000 s every run reaches 100% conversion and the sweep shows nothing;
       at 1000 s the slow runs are far from complete. Only 2 of the 7 indexes recorded the simulation time.
       Six months from now, you would not know which one you used.
    4. So ask for it explicitly, for example: *"Save each run to its own file, and write an index CSV with one row per run listing every
       parameter (including simulation time and solver settings) and the file name."*
